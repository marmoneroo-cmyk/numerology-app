# Subscriber Accounts (step 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Subscribers sign in, and their clients, readings and files live on the server, isolated from every other subscriber.
- An account works in one session at a time, on a limited number of devices.
- An admin opens, changes and suspends accounts.

**Architecture:** Supabase project `kcgjdxubcdmbrjlftxyv` (Frankfurt, Free plan for now) provides Auth, Postgres and Storage.
- **Database:** owns every access rule (row level security plus functions). One migration defines accounts, devices, the active session, the audit log and the workspace tables.
- **App:** keeps the store and its rules from step 2. A new `serverBackend` implements the same backend interface over RPCs and Storage, and passes the same contract suite (run on PGlite, Postgres in WebAssembly, with the real migration).
- **Studio:** sits behind an account gate. The public landing stays public.

**Tech Stack:**
- supabase-js 2.x with the publishable key, plus an Edge Function (Deno) holding the secret key.
- PGlite and Vitest for the database tests; React 18 and Vite for the app.

## Decisions

| Question | Decision | Why |
|---|---|---|
| What needs a login | The whole Studio (tools and workspace). The customer landing stays public | The spec: "the link alone is worth nothing" |
| Sign-up | Off. The admin opens each account with an email and a first password; the subscriber can change it | The built-in mailer reaches only the project team (2 per hour), so there are no invite or reset emails without a mail service |
| Password reset | The admin sets a new one (this also ends all of that account's sessions). Self-service by email comes with a mail service (e.g. Resend) | Same reason |
| One active session | Our own: `active_sessions` holds the one session per account that may use data, checked by RLS and by every workspace function | Supabase's single-session setting is Pro-only and lags by the token lifetime |
| After signing in | `signOut({ scope: 'others' })`, so other devices cannot even refresh | Free on every plan |
| Signing out | Ends the session at once: a session must still exist in `auth.sessions` | An access token otherwise lives up to an hour |
| Devices | A random key per browser.<br>Limit 2 (per account, adjustable), at most limit + 3 new devices in 30 days.<br>Subscribers can remove their other devices; admins can revoke any; admins are exempt | Without email codes, this plus one session makes sharing impractical and visible |
| Data | Each record is stored whole (`doc jsonb`) per collection and read and written through `ws_all`, `ws_get`, `ws_snapshot` and `ws_batch` (one transaction).<br>Files go to a private bucket at `ws-files/<user>/<id>` | The store's rules stay in one place; the database decides who sees what |
| Step-2 data on a device | Offered for upload to the account on first sign-in (a merge restore) | Nothing typed before accounts is lost |
| Watermark | "Licensed to: name · phone" in the Studio and on PDF reports | The spec's anti-sharing layer |
| Audit | Sign-ins and takeovers, devices added, refused or revoked, account changes, client deletions (id only), backups | The spec's privacy section |
| Plan limits to tell the owner | Free plan: pauses after a week idle, no backups, 1 GB of files. Move to Pro before selling | Owner decision (costs money) |

## Database API (all JSON in and out)

```
claim_session(p_device_key, p_label) -> {status: ok|suspended|device_revoked|device_limit|device_changes, profile, deviceId}
session_status(p_device_key)         -> {status: ok|replaced|suspended|device_revoked|signed_out}
my_devices()  revoke_my_device(p_device)  update_my_profile(p_full_name, p_phone)  log_event(p_action)
ws_all(p_store)  ws_get(p_store, p_id)  ws_snapshot()  ws_batch(p_ops)
admin_list_accounts()  admin_update_account(p_user, p_patch)  admin_list_devices(p_user)
admin_revoke_device(p_device)  admin_audit(p_user, p_limit)  am_i_admin()
Edge Function admin-accounts: {action: "create", email, password, fullName, phone, plan} | {action: "set_password", userId, password}
```
